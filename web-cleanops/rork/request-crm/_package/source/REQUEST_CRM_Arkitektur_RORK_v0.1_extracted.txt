1. Executive summary och målbild

MålbildBygg en intern REQUEST Platform som blir systemets centrala kommunikations- och operationslager. Plattformen ska hantera ärenden, chatt, notifikationer, AI-intake, intern samordning, e-postersättning, behörighet och operativ kontroll. Kunder och medarbetare ska inte bjudas in förrän helheten är färdigbyggd, testad med realistisk testdata och produktionsdata är rensad från testtransaktioner.

REQUEST ska inte implementeras som ett traditionellt support-ticket-system. Plattformen ska byggas som en modulär kommunikationsplattform med en gemensam domain model för ärenden, meddelanden, trådar, notifikationer, chatt, AI-förslag, interna arbetsuppgifter, lässtatus, audit och behörighet.

Huvudmål

Ersätta e-post och stora delar av telefonhantering för kund- och medarbetarkommunikation.

Ge admin och arbetsledning en operativ kontrollvy över pågående kommunikation, avvikelser och kritiska händelser.

Ge kunder och medarbetare en kontrollerad väg in via AI-chatt, kategoriserade ärenden och portalkommunikation.

Stödja intern samordning i samma ärende via arbetsuppgifter, interna kommentarer och individuella läs-/bekräftelsestatusar.

Förbereda för AI-driven intake, kategorisering, sammanfattning, svarsförslag och senare reglerad automation.

Strategiskt beslut

Ärendehanteraren, chatten och notifikationscentret ska byggas under samma arkitektur innan extern lansering.

Implementation ska ändå göras stegvis, med feature flags och vertikala testflöden.

AI ska designas från dag ett men kopplas på med mock-adapter först och riktig API-integration först när kärnflödena är stabila.

REQUEST Platform|-- Request Manager: långlivade ärenden, ansvar, historik och SLA|-- Notification Center: operativa signaler, prio, emergency och åtkomstförfrågningar|-- Chat: AI-first intake, live admin takeover och eskalering till ärende|-- Dashboard: saker att se över, avvikelser och kontrollvyer|-- AI Assistant Layer: mock först, provider-adapter senare, tool-baserade actions

3. Scope, non-goals och release-strategi

3.1 Scope

Ärendehanterare för admin, kund, medarbetare, system och AI.

Chatt med AI-assistent som primär intake-kanal för kund/medarbetare.

Notifikationscenter för systemhändelser, prio, emergency och informationsnotiser.

Interna arbetsuppgifter och interna inlägg inom ärenden.

Behörighetsmodell med owner, support, category, locked access, preview och request access.

Snooze/dölj-logik, handlägg själv/dölj för kollegor och låsta ärenden.

E-postnotifiering, fördröjd skicklogik och förberedd inbound email-reply-funktion.

Testmode, seed data, test batch cleanup och miljöstrategi.

AI-service med mock-adapter först och provider-adapter senare.

3.2 Non-goals i första tekniska scope

Full visuell regelmotor i settings från start.

Full autonom AI som stänger ärenden utan admin-godkännande.

Full avboknings-/ombokningsmotor med schema- och fakturapåverkan från första iterationen.

Full livechat-routing med avancerad köhantering från första iterationen.

Extern lansering till kund/medarbetare innan modulen är testad end-to-end.

3.3 Release-strategi

Bygg allt internt före extern lansering.

Använd feature flags så att funktioner kan byggas och testas utan att aktiveras globalt.

Använd staging/test-tenant med realistisk testdata.

Rensa testdata via script/test batch cleanup innan produktionsexponering.

Anslut AI API först efter att mock-AI-flöden fungerar med chatt, ärende, notifikationer och admin approval.

4. Arkitekturprinciper

Princip

Teknisk innebörd

Motivering

Single communication domain

Ärenden, chat, notiser och meddelanden delar gemensamma kärnobjekt där det är möjligt.

Undviker tre separata kommunikationssystem.

Request as container

Ett ärende är en container för trådar, interna posts, tasks, system events, AI-sammanfattningar och metadata.

Skalbart för komplexa ärenden med flera parter.

Event-driven core

SystemEvent skapas av moduler och mappas via rules till notification, dashboard item, task eller request.

Separera händelser från åtgärder.

RBAC + ABAC

Roller kombineras med attribut: owner, support, category, participant, lock state, tenant, sensitivity.

Krävs för låsta ärenden och begränsad synlighet.

Audit everything

Alla statusbyten, access events, AI actions, mail sends, snooze och visibility changes loggas.

Spårbarhet, felsökning och ansvar.

Mock-first AI

AI-service implementeras med mock-adapter innan riktig provider kopplas på.

Testa systemlogik utan AI-osäkerhet.

Provider isolation

Systemet ska prata med Internal AI Service, inte OpenAI direkt från varje modul.

Bytbar provider, bättre loggning, policy och fallback.

Outbox pattern

E-post och externa notifieringar bör skickas via queue/outbox, inte direkt i request transaction.

Robust leverans, retries och audit.

Feature flags

Varje större funktion aktiveras via flagg per miljö/tenant/roll.

Säker intern testning före release.

No silent hiding

Snooze/hidden får aldrig dölja obekräftade eller tidskritiska uppgifter från ansvariga.

Förhindrar att ärenden faller mellan stolarna.

7. Ärendehanteraren

DefinitionÄrendehanteraren är systemets långlivade kommunikations- och ansvarslager. Den ersätter e-post som arbetsyta, inte bara som meddelandekanal.

7.1 Hårdkodade ärendetyper från start

Avbokning / Ombokning

Kund vill boka tjänst [vald tjänst]

Reklamation

Något har gått sönder

Kundinformation

Fakturafråga

Ställ en fråga / generellt meddelande

Fråga om lön

Schema - samlat systemärende för schemarelaterade ändringar

Utöver hårdkodade ärendetyper ska admin kunna skapa egna ärendetyper/kategorier i settings. Full dynamisk formulärbyggare behöver inte vara första iterationen, men datamodellen ska inte blockera typ-specifika metadata senare.

7.2 Ärendevy: trekolumnslayout

Kolumn

Innehåll

Teknisk funktion

Vänster: Intern yta

Intern kommunikation, arbetsuppgifter, telefonsamtal, anteckningar, AI summary, interna kommentarer.

Endast admin/behörig intern personal. Har egna posts, task-assignees och acknowledgement-status.

Mitten: Extern kommunikation

Konversation med kund, medarbetare, kund+medarbetare eller AI.

Flera RequestThreads med tydlig visibility_scope. Admin ska se mottagare innan meddelande skickas.

Höger: Ärendeinformation

Kategori, status, prioritet, severity, SLA, kund, medarbetare, ägare, support, bokning, faktura, AO, snooze, låsning, e-postpolicy.

Metadata och actions. Här ligger knappar för snooze, handlägg själv, låsning, access och e-postinställningar.

7.3 Skapa ärende

Alla aktörer kan skapa ärenden: admin, kund, medarbetare, system och AI.

Alla aktörer har olika behörighet och olika synliga kategorier.

Kund/medarbetare ska kunna välja ärendetyp eller välja "Skicka meddelande till kontoret".

Om kunden väljer "Skicka meddelande till kontoret" ska AI-intake starta utan initial kategori/prioritet.

AI ska samla kontext, ställa följdfrågor, föreslå kategori, prioritet, summary och tasks.

Om AI kan lösa ärendet ska admin i början kunna godkänna stängning och läsa konversationen innan slutlig closure.

Om AI inte kan lösa ärendet ska AI skapa ärendeutkast eller ärende enligt policy.

7.4 Kopplingar på ärendet

customer_id: max en kund per ärende.

employee_ids: en eller flera medarbetare, t.ex. städpersonal.

support_admin_ids: en eller flera admin/arbetsledare.

owner_admin_id: huvudansvarig, rekommenderat max en ägare.

booking_id: valfri koppling till bokning.

work_order_id: valfri koppling till arbetsorder.

invoice_id: valfri koppling till faktura.

media_attachment_ids: filer/bilder.

source_event_id: systemhändelse som skapade ärendet.

chat_session_id: om ärendet kommer från chatt.

7.5 Status, priority, severity och SLA

Begrepp

Rekommenderade värden

Får inte blandas ihop med

Status

Nytt, Öppet, Pågår, Väntar på kund, Väntar på medarbetare, Väntar internt, Åtgärd planerad, Löst, Stängt, Återöppnat.

Status är inte priority eller emergency.

Priority

Low, Normal, High.

Priority anger verksamhetsvikt, inte nödvändigtvis akut UI-popup.

Severity

Normal, Prio, Emergency.

Severity styr prio-routing, färg och popup.

SLA/deadline

Respond due, resolve due, internal task due.

SLA styr förfall och prioriterade vyer.

8. Kommunikationsslingor och synlighet

KärnregelEtt ärende kan innehålla flera externa kommunikationsslingor. Kund och medarbetare ska som default inte se varandras trådar. Gemensam tråd ska kräva aktivt val av admin eller explicit systemregel.

Trådtyp

Synlig för

Användning

customer

Admin + specifik kund

Kunddialog. Kunden ser denna tråd i portal och via e-post.

employee

Admin + specifik medarbetare

Medarbetardialog. Kunden ser inte denna.

shared_customer_employee

Admin + kund + en/flera medarbetare

Endast när admin aktivt vill att båda parter ska se samma dialog.

internal

Admin/support/ägare enligt access

Intern kommunikation. Ska inte visas för kund/medarbetare.

ai_intake

AI + kund/medarbetare, senare admin

Intake-konversation som kan sammanfattas till ärende.

Admin UI måste visa mottagare innan skick: "Detta skickas till Anna Andersson" eller "Internt - syns inte för kund/medarbetare".

Externa meddelandens synlighet ska inte kunna ändras i efterhand utan särskild audit och admin-behörighet. Rekommendation: blockera ändring av extern visibility efter skick.

Kund ser endast kundsynliga trådar, kundsynliga bilagor och förenklad status.

Medarbetare ser endast medarbetarsynliga trådar och förenklad status.

Admin ser alla trådar inom access scope.

9. Interna arbetsuppgifter och interna inlägg

ProduktvärdeDet interna fältet i ärendet ska fungera som ett mini-task-system. Detta är en av de högst värderade funktionerna och ska inte reduceras till vanliga anteckningar.

9.1 Inläggstyper

Arbetsuppgift ska vara hårdkodad post_type eftersom den kräver assignment, status, kommentartråd och acknowledgements.

Telefonsamtal, anteckning och andra inläggstyper ska kunna läggas till i settings senare.

AI-sammanfattning och systemnotering kan vara systemgenererade interna posts.

9.2 Task assignment och acknowledgement

Request 5551  InternalPost: Arbetsuppgift 1 - Ring kund    Assignees: Sebastian    Comments: ...  InternalPost: Arbetsuppgift 2 - Uppdatera städprotokoll    Assignees: none -> visas som otilldelad  InternalPost: Arbetsuppgift 3 - Uppdatera AO-anteckningar    Assignees: Marcus, Sebastian    Acknowledgement:      Marcus = blue / not acknowledged      Sebastian = green / acknowledged

Kommentar på arbetsuppgift ska notifiera tilldelade admin på just den arbetsuppgiften.

Om Sebastian är ensam tilldelad på Arbetsuppgift 1 och Sebastian svarar, ska ingen annan notifieras.

Om Sebastian vill involvera Marcus ska Sebastian kunna lägga till Marcus via plusikon på arbetsuppgiften.

När Marcus läggs till får Marcus notis och arbetsuppgiften blir obekräftad för Marcus.

Att öppna ärendet ska inte automatiskt markera interna arbetsuppgifter som lästa. Admin måste öppna/klicka relevant post.

9.3 Read states

Nivå

Trigger

Konsekvens

10. Snooze, handlägg själv och låsta ärenden

Viktigt begreppsbeslutDessa funktioner får inte blandas ihop. Snooze är listfiltrering. Handlägg själv är aktivt ägarskap/arbetsfördelning. Låst ärende är access control.

10.1 Snooze / Dölj tillfälligt

10.2 Handlägg själv / Dölj för kollegor

Ärendet ligger kvar i kategorin, t.ex. Kundtjänst.

Ärendet visas aktivt bara för owner och ansluten support.

Kollegor i samma kategori får inte ärendet i sina normala aktiva listor.

Nya kund-/medarbetarmeddelanden gör inte ärendet aktivt för kollegor; bara owner/support notifieras.

Detta är inte privat ärende. Supervisor/superadmin ska kunna se via översikt.

Systemet bör visa kontrollvy för ärenden som handläggs själv länge eller där owner är inaktiv/frånvarande.

10.3 Låsta ärenden och access request

Ett låst ärende ska kunna hittas via kund-/medarbetarsökning men innehållet är dolt.

Admin utan access ser begränsad metadata och knapp: Begär åtkomst.

Owner/support får notifikation i Notification Center: "Admin X begär åtkomst till ärende Y".

Owner/support kan acceptera eller neka.

Beslut skapar notifikation till begärande admin.

Acceptera bör kunna ha nivåer: read-only, add as support, owner transfer.

Superadmin / behörig lead ska kunna override:a låsta ärenden. Override loggas tydligt.

Om owner är frånvarande eller inte svarar inom X tid ska access request eskaleras.

Visibility-flow

Dölj för mig fungerar.

Dölj för alla fungerar men döljer inte för admin med obekräftad task.

Quick hide döljer globalt i 2 dagar.

Handlägg själv döljer för kollegor men inte owner/support.

Notification-flow

Sen incheckning skapar notification, inte request.

Notification länkar korrekt till employee/booking/customer.

Production-data påverkas inte.
